# 写作规则

## 硬性禁令（违反必改）

1. **不提 GitHub stars**：标题、正文、结语任何位置都不出现 star 数或 stars 相关描述
2. **不提作者/赞助信息**：不写「作者是 XX」「由 XX 赞助支持」
3. **不引用其他文章**：不写「上一篇文章聊了……」「前几篇我们讲过……」，每篇独立成文
4. **不列下载链接清单**：不写「或直接下载：macOS · Windows · Linux」「移动端：iOS App Store · Android APK」这类行内链接列表
5. **安装方式只留一条**：最简的一条命令（brew install 或 curl），其余安装路径删掉
6. **不做「全解读」承诺**：标题不写「全解读」，写「工程拆解」「梳理」等
7. **文末不留项目地址/文档链接清单**：结尾只收观点，不留一串 URL

## 禁用句式（对比脚手架）

详见 [banned-patterns.md](banned-patterns.md)。检查器会拦截，人工也要有意识：

- `不是……而是……` / `不只是……而是……` / `不……而是……` / `而不是`
- `不是……是……` 同类句式（检查器暂不覆盖，人工把关）

## 结构规范

- **开头直接切入**：一句定位 + 核心能力，不铺垫背景故事
- **章节编号**：一、二、三……+ 结语，每章有小标题
- **代码块/表格优先**：技术细节用代码块和表格呈现，不用长段落
- **每条特性 = 是什么 + 效果**：讲完「是什么」「怎么配」必须讲「带来什么」
- **结语收束**：观点总结，不预告下一篇，不留外链清单

## 风格规范

- 短句为主，少分析腔、少翻译腔、少研究摘要体
- 用「能看出」「主要反映」这类自然表述，避免「更适合」「不太适合」类报告句式
- 数据只写经核实的（README/docs 里有依据的），推断要标注
- 不写「值得一夸」「很有意思」「极致」类主观评价
