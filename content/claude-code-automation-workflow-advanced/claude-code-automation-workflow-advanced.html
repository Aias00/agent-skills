title: Claude Code 自动化工作流实战：构建内容生产流水线
description: 以内容生产为例，系统讲解 Hooks、MCP、Skills 三驾马车的组合使用，搭建从写作到发布的完整自动化链路。

先说结论

Claude Code 的自动化能力由三驾马车构成：Hooks 负责事件触发，MCP 负责外部能力扩展，Skills 负责任务封装复用。理解它们的边界和组合方式，就能搭建出真正省心的自动化工作流。

这篇文章以一个真实场景——「从 Markdown 草稿到公众号发布」——为线索，给出完整可复制的配置文件和代码。你看完就能照着搭一套自己的内容生产流水线。

一、自动化工作流的三驾马车

很多同学问我：「我想让 Claude Code 自动帮我做事，到底该用 Hooks、MCP 还是 Skills？」

答案是：它们不是互斥的，而是各司其职。

1.1 Hooks：零成本的事件触发器

Hooks 是 Claude Code 的生命周期钩子。你不需要启动额外进程，只需要在 settings.json 里配置一下，Claude 就会在特定时机自动执行你的脚本。

典型用途：

钩子 触发时机 典型用途
PreToolUse 调用工具前 拦截危险命令、自动加参数
PostToolUse 调用工具后 记录日志、通知
Stop 会话结束时 自动保存、清理、汇总

一个最简单的例子——会话结束时自动保存：

// ~/.claude/settings.json
{
  "hooks": {
    "Stop": [
      {
        "hooks": [
          {
            "type": "command",
            "command": "git add . && git commit -m 'auto: save at $(date +%Y%m%d-%H%M)'"
          }
        ]
      }
    ]
  }
}

注意： Stop 钩子不支持 matcher。只有 PreToolUse 和 PostToolUse 支持 matcher 来匹配工具名称。

Hooks 的限制：
- 只能「触发时执行」，无法持久化状态
- 无法访问 Claude 的内部上下文（比如对话历史）
- 脚本执行时间不宜过长（默认 60 秒超时）

1.2 MCP：给 Claude 装上外部能力的插件

MCP（Model Context Protocol）是 Anthropic 推出的标准化协议，让 Claude 能够访问外部数据和工具。它是一个独立进程，通过 stdio 或网络与 Claude Code 通信。

典型用途：

MCP Server 能力
filesystem 读写本地文件（受限目录）
postgres 查询 PostgreSQL 数据库
brave-search 网络搜索
puppeteer 浏览器自动化

配置示例：

// ~/.claude/settings.json
{
  "mcpServers": {
    "filesystem": {
      "command": "npx",
      "args": ["-y", "@modelcontextprotocol/server-filesystem", "/Users/you/articles"]
    },
    "brave-search": {
      "command": "npx",
      "args": ["-y", "@modelcontextprotocol/server-brave-search"],
      "env": {
        "BRAVE_API_KEY": "your-api-key"
      }
    }
  }
}

MCP 的成本：
- 每个 MCP server 都是一个独立进程，占用内存
- 启动需要时间（几十毫秒到几秒）
- 需要额外的权限配置

1.3 Skills：可复用的任务封装

Skills 是把复杂的多步骤任务打包成可复用的模块。一个 Skill 就是一个目录，里面有一份 SKILL.md 文件描述任务流程。

典型用途：
- 代码审查流程
- 文章审阅与格式化
- 项目初始化模板

最小化 Skill 结构：

~/.claude/skills/article-init/
├── SKILL.md          # 技能描述与执行步骤
├── scripts/          # 配套脚本（可选）
│   └── init.sh
└── references/       # 参考文档（可选）
    └── template.md

SKILL.md 示例：

---
name: article-init
description: 从模板创建新文章
triggers:
  - "创建文章"
  - "新文章"
---

## 执行步骤

1. 询问用户文章主题和类型（技术/转载/随笔）
2. 在 articles/workspaces/ 下创建目录
3. 从模板复制初始文件结构
4. 初始化 Git 分支：`git checkout -b article/{article-name}`
5. 打开编辑器

Skills 的优势：
- 可分享、可版本控制
- 团队统一流程
- 比 MCP 轻量，比 Hooks 强大

1.4 选型决策树

用一个流程图总结：

需要访问外部数据/工具？
├── 是 → 用 MCP
└── 否 → 只是触发时执行脚本？
         ├── 是 → 用 Hooks
         └── 否 → 多步骤任务需要复用？
                  ├── 是 → 用 Skills
                  └── 否 → 直接对话就够了

但实际场景中，三者经常组合使用：

  • Hook 触发 Skill 执行（会话结束时自动审阅）
  • Skill 内部调用 MCP（审阅时查询数据库）
  • MCP 结果触发 Hook（查询完成后发送通知）

二、场景拆解：内容生产的四个阶段

自动化不是「一个指令搞定所有」。越是复杂的流程，越需要拆解。

2.1 拆解原则

好的拆解要满足三个条件：
1. 清晰的输入输出——每个阶段接收什么、产出什么，一目了然
2. 可独立调试——出了问题能快速定位是哪个阶段
3. 可灵活组合——今天只自动化两个阶段，明天再加一个，互不影响

2.2 四阶段流程图

以「从草稿到发布」为例：

┌─────────────┐    ┌─────────────┐    ┌─────────────┐    ┌─────────────┐
│   写作      │───▶│   审阅      │───▶│   格式化    │───▶│   发布      │
└─────────────┘    └─────────────┘    └─────────────┘    └─────────────┘
      │                  │                  │                  │
      ▼                  ▼                  ▼                  ▼
 灵感/素材          Markdown草稿       审阅报告+修订稿      多平台HTML       文章链接

2.3 各阶段详解

写作阶段

输入： 灵感、素材、大纲
输出： Markdown 草稿文件

自动化点：
- 自动保存（Hook: Stop 时 Git 提交）
- 草稿版本管理（按时间戳备份）
- 模板初始化（Skill: article-init）

触发条件： 手动启动（写作是创造性工作，不宜过度自动化）

审阅阶段

输入： Markdown 草稿
输出： 审阅报告 + 修订后的草稿

自动化点：
- 技术正确性检查（Skill: technical-article-review）
- 禁用词扫描（脚本：check_banned_scaffolding.py）
- 风格一致性检查（自定义规则）

触发条件： 文件保存后自动触发，或手动调用

格式化阶段

输入： 审阅后的 Markdown
输出： 平台适配的 HTML（微信/头条/博客）

自动化点：
- Markdown → HTML 转换（Skill: wechat-article-formatter）
- 主题选择与样式注入
- 图片处理与优化

触发条件： 审阅通过后

发布阶段

输入： 格式化后的 HTML + 封面图
输出： 文章链接

自动化点：
- 封面图自动生成（脚本：generate-cover-image.py）
- API 推送（Skill: wechat-publisher）
- 发布结果通知（Hook: Stop 时汇总）

触发条件： 格式化完成且封面就绪

2.4 与现有工具的对应

这个仓库里已经有现成的 Skills 可以直接用：

阶段 现有工具 位置
写作 article-init（需创建） -
审阅 technical-article-review ../technical-article-review/
格式化 wechat-article-formatter ../wechat-article-formatter/
发布 wechat-publisher ../wechat-publisher/

三、实战：搭建文章生产流水线

这一章是整篇文章的核心。我会给出完整可复制的配置和代码，你照着做就能跑起来。

3.1 环境准备

目录结构：

articles/
├── workspaces/      # 草稿区
│   └── my-article/
│       ├── my-article.md
│       └── imgs/
├── publishing/      # 待发布
└── archives/        # 已发布

依赖安装：

cd wechat-article-formatter
python3 -m venv .venv
.venv/bin/pip install -r requirements.txt

cd ../wechat-publisher
bun install
bun scripts/bootstrap-local.ts --project-root ..

3.2 写作阶段：自动保存与版本管理

先解决一个痛点：写着写着忘了保存，或者想找回之前的版本。

Hook 配置——会话结束时自动提交：

// ~/.claude/settings.json
{
  "hooks": {
    "Stop": [
      {
        "hooks": [
          {
            "type": "command",
            "command": "cd /path/to/articles/workspaces && git add . && git commit -m 'auto: draft save at $(date +%Y%m%d-%H%M)' 2>/dev/null || true"
          }
        ]
      }
    ]
  }
}

注意几点：
- Stop 钩子不支持 matcher，会在所有会话结束时触发，所以命令中要用完整路径
- 2>/dev/null || true 防止「没有变更」时报错
- 提交信息带时间戳，方便后续筛选
- 如果只想在特定目录触发，可以在命令开头加条件判断：[ -d "articles/workspaces" ] && ...

创建新文章的 Skill：

<!-- ~/.claude/skills/article-init/SKILL.md -->
---
name: article-init
description: 从模板创建新文章
triggers:
  - "创建文章"
  - "新文章"
---

## 执行步骤

1. 询问用户文章主题（用于生成目录名）
2. 询问文章类型：
   - 技术文章 → 使用 technical 模板
   - 转载文章 → 使用 repost 模板
   - 随笔 → 使用 essay 模板
3. 在 articles/workspaces/ 下创建目录：`{主题slug}/`
4. 创建文件结构：
   - `{主题slug}.md`（从模板复制）
   - `imgs/` 目录
5. 初始化 Git 分支：`git checkout -b article/{主题slug}`
6. 输出：已创建文章，可以开始写作

## 模板

技术文章模板 frontmatter：

title: {标题}
created: {日期}
status: draft
type: tech

踩坑经验：
- Git 提交信息格式要规范，方便后续用 git log --oneline 筛选
- 如果工作目录不在 Git 仓库根目录，cd 命令要写完整路径
- Hook 执行时没有交互环境，不要用 git commit 不带 -m

3.3 审阅阶段：质量检查流水线

写完草稿后，需要检查技术正确性和「AI 味道」。

调用 technical-article-review Skill：

> 用 technical-article-review 审阅 articles/workspaces/my-article/my-article.md

这个 Skill 会检查：
- 技术内容正确性
- 逻辑连贯性
- 是否有未解释的术语
- 代码示例是否可运行

补充脚本：禁用词扫描

有些表达方式太「AI 味道」，比如「不是……而是……」「也就是说」。仓库里自带一个检测脚本：

python3 ../technical-article-review/scripts/check_banned_scaffolding.py --input articles/workspaces/my-article/my-article.md

输出示例：

成功时：

OK: no banned scaffolding patterns found in prose

发现问题 时：

Blocked: banned scaffolding patterns found
line 42: 不是……而是…… -> 这不是简单的工具，而是完整的开发环境

踩坑经验：
- technical-article-review 默认会直接修改文章，如果你想只看报告不改文章，明确说「只审不改」或 review-only
- 禁用词检查会自动排除代码块和引用块，避免误报
- 这个脚本是硬阻断模式：有错误就退出码非零，可以配合 CI 使用

3.4 格式化阶段：一键生成多平台 HTML

审阅通过后，生成适配微信公众号的 HTML。

调用 wechat-article-formatter：

wechat-article-formatter/.venv/bin/python \
  wechat-article-formatter/scripts/markdown_to_html.py \
  --input /Users/you/articles/workspaces/my-article/my-article.md \
  --theme mist-blue \
  --output /Users/you/articles/workspaces/my-article/my-article.html \
  --preview

参数说明：
- --input：Markdown 源文件（建议用绝对路径）
- --theme：主题样式，可选值见下表
- --output：输出的 HTML 文件路径
- --preview：生成后自动打开浏览器预览

可用主题：

主题 适用场景
mist-blue 技术文章（默认，雾霾蓝）
ai-tech AI 主题、产品展示
tech-blue 科技感
forest-green 自然主题
sunset 暖色调
slate 中性专业
midnight 深色主题
warm-orange 活力风格

踩坑经验：
- 图片路径要用相对路径（相对于 Markdown 文件），或者用 imgs/xxx.png 格式
- 微信编辑器会过滤 <style> 标签，所以 formatter 用的是内联样式
- --preview 在无头服务器上会报错，可以去掉

3.5 发布阶段：封面生成与 API 推送

自动生成封面图：

python3 ../wechat-publisher/scripts/generate-cover-image.py \
  --markdown /Users/you/articles/workspaces/my-article/my-article.md \
  --out /Users/you/articles/workspaces/my-article/imgs/cover.png \
  --bootstrap-pillow

--bootstrap-pillow 会在缺少 Pillow 库时自动安装。

发布到微信公众号：

cd ../wechat-publisher

bun scripts/check-permissions.ts --project-root ..

bun scripts/wechat-publish.ts /Users/you/articles/workspaces/my-article/my-article.md --dry-run

bun scripts/wechat-publish.ts /Users/you/articles/workspaces/my-article/my-article.md

踩坑经验：
- 封面图比例要求 2.35:1，尺寸至少 900×383
- 如果没有封面图，会按顺序尝试：frontmatter 中的 coverImage → imgs/cover.png → 文章第一张图
- API 有频率限制，批量发布时注意间隔

3.6 完整流水线脚本

把上面所有步骤串起来，用一个 Makefile：

ARTICLE ?= articles/workspaces/my-article/my-article.md
ARTICLE_DIR := $(dir $(ARTICLE))
ARTICLE_NAME := $(basename $(notdir $(ARTICLE)))

.PHONY: review format cover publish all

review:
    @echo "📋 审阅文章..."
    python3 ../technical-article-review/scripts/check_banned_scaffolding.py --input $(ARTICLE)

format:
    @echo "🎨 格式化..."
    ../wechat-article-formatter/.venv/bin/python \
        ../wechat-article-formatter/scripts/markdown_to_html.py \
        --input $(ARTICLE) \
        --theme mist-blue \
        --output $(ARTICLE_DIR)$(ARTICLE_NAME).html

cover:
    @echo "🖼️ 生成封面..."
    python3 ../wechat-publisher/scripts/generate-cover-image.py \
        --markdown $(ARTICLE) \
        --out $(ARTICLE_DIR)imgs/cover.png

publish: review format cover
    @echo "🚀 发布..."
    cd ../wechat-publisher && bun scripts/wechat-publish.ts ../content/$(ARTICLE)

all: review format cover
    @echo "✅ 流水线完成，可以发布了"

使用方式：

make review ARTICLE=articles/workspaces/my-article/my-article.md

make format ARTICLE=articles/workspaces/my-article/my-article.md

make cover ARTICLE=articles/workspaces/my-article/my-article.md

make all ARTICLE=articles/workspaces/my-article/my-article.md

make publish ARTICLE=articles/workspaces/my-article/my-article.md

四、进阶模式

基础流水线搭好后，可以进一步优化。

4.1 并行执行多个任务

场景：同时生成微信、头条、博客三个平台的 HTML。

#!/bin/bash

ARTICLE=$1
BASENAME=$(basename "$ARTICLE" .md)
DIR=$(dirname "$ARTICLE")

wechat-article-formatter/.venv/bin/python \
  wechat-article-formatter/scripts/markdown_to_html.py \
  --input "$ARTICLE" --theme mist-blue \
  --output "$DIR/$BASENAME-wechat.html" &

wechat-article-formatter/.venv/bin/python \
  wechat-article-formatter/scripts/markdown_to_html.py \
  --input "$ARTICLE" --theme tech-blue \
  --output "$DIR/$BASENAME-toutiao.html" &

wechat-article-formatter/.venv/bin/python \
  wechat-article-formatter/scripts/markdown_to_html.py \
  --input "$ARTICLE" --theme forest \
  --output "$DIR/$BASENAME-blog.html" &

wait

echo "✅ 三个平台的 HTML 已生成"

注意事项：
- & 把任务放到后台，wait 等待所有后台任务完成
- 避免多个进程同时写同一个文件
- 如果任务之间有依赖，不能并行

4.2 错误恢复与重试

API 调用可能失败，需要自动重试。

// retry.ts
async function withRetry<T>(
  fn: () => Promise<T>,
  options: {
    maxRetries: number;
    baseDelayMs: number;
    name?: string;
  }
): Promise<T> {
  let lastError: Error | null = null;
  let delay = options.baseDelayMs;

  for (let attempt = 1; attempt <= options.maxRetries; attempt++) {
    try {
      const result = await fn();
      if (attempt > 1) {
        console.log(`✅ ${options.name || '操作'} 在第 ${attempt} 次重试后成功`);
      }
      return result;
    } catch (error) {
      lastError = error as Error;
      console.log(
        `⚠️ ${options.name || '操作'} 第 ${attempt} 次失败: ${lastError.message}`
      );

      if (attempt < options.maxRetries) {
        console.log(`   ${delay}ms 后重试...`);
        await new Promise((resolve) => setTimeout(resolve, delay));
        delay *= 2; // 指数退避
      }
    }
  }

  throw lastError;
}

// 使用示例
const result = await withRetry(
  () => publishToWechat(article),
  { maxRetries: 3, baseDelayMs: 1000, name: '发布到微信' }
);

踩坑经验：
- 重试次数 3 次足够，太多会浪费等待时间
- 指数退避（每次延迟翻倍）比固定延迟更友好
- 确保操作是幂等的——多次执行结果相同

4.3 条件分支：根据文章类型选择流程

不同类型的文章，处理流程不同：

  • 技术文章：审阅 → 格式化 → 发布
  • 转载文章：只格式化 → 发布
  • 草稿：只保存备份

在 Skill 中实现条件判断：

<!-- ~/.claude/skills/article-process/SKILL.md -->
---
name: article-process
description: 根据文章类型执行不同处理流程
triggers:
  - "处理文章"
  - "文章流程"
---

## 执行逻辑

1. 读取文章 frontmatter 中的 `type` 字段
2. 根据类型执行不同流程：

**type: tech（技术文章）**
1. 运行技术审阅
2. 运行禁用词检查
3. 格式化为 HTML
4. 生成封面图
5. 询问是否发布

**type: repost（转载文章）**
1. 格式化为 HTML
2. 生成封面图
3. 询问是否发布

**type: draft（草稿）**
1. 仅保存备份
2. 提示「草稿已保存」

3. 更新 frontmatter 中的 `status` 字段

在 Hook 中根据文件类型触发：

PreToolUse 和 PostToolUse 支持 matcher，可以用来根据工具名称触发：

{
  "hooks": {
    "PreToolUse": [
      {
        "matcher": "Write|Edit",
        "hooks": [
          {
            "type": "command",
            "command": "echo 'File modified' >> /tmp/changes.log"
          }
        ]
      }
    ]
  }
}

但 Stop 钩子不支持 matcher。如果需要条件触发，要在脚本内部判断：

#!/bin/bash
if [ -d "articles/workspaces" ]; then
  make review
fi

4.4 状态管理与追踪

用 frontmatter 记录文章状态，是最轻量的方案：

---
title: 我的文章
status: draft      # draft → reviewing → ready → published
type: tech
created: 2024-01-15
updated: 2024-01-16
reviewed_at:       # 审阅完成后填写
published_at:      # 发布完成后填写
published_url:     # 发布后的文章链接
---

状态更新脚本：

#!/bin/bash

FILE=$1
NEW_STATUS=$2

sed -i.bak "s/^status:.*/status: $NEW_STATUS/" "$FILE"

sed -i.bak "s/^updated:.*/updated: $(date +%Y-%m-%d)/" "$FILE"

if [ "$NEW_STATUS" = "published" ]; then
  sed -i.bak "s/^published_at:.*/published_at: $(date +%Y-%m-%d)/" "$FILE"
fi

rm -f "${FILE}.bak"
echo "✅ 状态已更新为: $NEW_STATUS"

4.5 监控与日志

知道每次自动化执行的结果，方便排查问题。

// logger.ts
interface LogEntry {
  timestamp: string;
  level: 'info' | 'warn' | 'error';
  stage: 'write' | 'review' | 'format' | 'publish';
  article?: string;
  message: string;
  duration?: number;
}

function log(entry: Omit<LogEntry, 'timestamp'>) {
  const fullEntry: LogEntry = {
    ...entry,
    timestamp: new Date().toISOString(),
  };

  // 输出到文件
  const logLine = JSON.stringify(fullEntry);
  const logFile = `${process.env.HOME}/.claude/article-pipeline.log`;
  require('fs').appendFileSync(logFile, logLine + '\n');

  // 同时输出到控制台
  const prefix = entry.level === 'error' ? '❌' : entry.level === 'warn' ? '⚠️' : '✅';
  console.log(`${prefix} [${entry.stage}] ${entry.message}`);
  if (entry.duration) {
    console.log(`   耗时: ${entry.duration}ms`);
  }
}

// 使用示例
const start = Date.now();
await formatArticle(article);
log({
  level: 'info',
  stage: 'format',
  article: article,
  message: '格式化完成',
  duration: Date.now() - start,
});

五、踩坑经验与最佳实践

5.1 配置调试技巧

Hook 不触发：
1. 检查 JSON 语法：cat ~/.claude/settings.json | python3 -m json.tool
2. 检查 matcher 正则是否正确（可以用在线正则测试）
3. 查看 Claude Code 日志：~/.claude/logs/

MCP 连不上：
1. 独立启动 server 测试：npx @modelcontextprotocol/server-filesystem /your/path
2. 检查端口占用：lsof -i :端口号
3. 检查命令路径：用绝对路径更稳妥

Skill 无响应：
1. 确认文件位置：ls ~/.claude/skills/my-skill/SKILL.md
2. 检查触发词：SKILL.md 中的 triggers 是否匹配你说的话
3. 确认 Skill 已加载：在 Claude Code 中输入 / 查看列表

5.2 常见错误排查

错误现象 可能原因 解决方案
Hook 不执行 JSON 格式错误 python3 -m json.tool 验证
MCP 超时 进程未启动 检查 server 状态，重启 Claude Code
Skill 无响应 触发词不匹配 检查 SKILL.md 中的 triggers
脚本权限错误 缺少执行权限 chmod +x script.sh
路径找不到 工作目录错误 使用绝对路径
API 调用失败 权限不足 运行 check-permissions.ts
封面图生成失败 缺少 Pillow 加 --bootstrap-pillow 参数
HTML 样式丢失 微信过滤 确认使用内联样式
Git 提交失败 没有变更 加 2>/dev/null \|\| true

5.3 性能优化建议

减少不必要的 Hook 触发：

// 不好：全局匹配
"matcher": ""

// 好：精准匹配
"matcher": "articles/workspaces/.*\\.md$"

MCP server 按需启动：

低频使用的 MCP 不要常驻，用到了再启动。

// 只配置你需要的 MCP server
{
  "mcpServers": {
    "frequently-used": {
      "command": "npx",
      "args": ["-y", "my-frequent-server"]
    }
    // 不配置低频 server，需要时再添加
  }
}

提示： 可以用命令行动态管理 MCP server：

claude mcp list

claude mcp add my-server -- npx -y my-server

claude mcp remove my-server

并行任务并发控制：

ls *.md | xargs -P 3 -I {} ./process.sh {}

缓存审阅结果：

如果文章没变，不需要重复审阅。可以在 frontmatter 中记录 hash：

---
content_hash: abc123  # 文章内容的 hash
reviewed_at: 2024-01-15
---

5.4 安全注意事项

不要硬编码敏感信息：

// 不好
{
  "mcpServers": {
    "my-server": {
      "env": {
        "API_KEY": "sk-xxxxx"  // 不要这样写！
      }
    }
  }
}

// 好：使用环境变量
{
  "mcpServers": {
    "my-server": {
      "env": {
        "API_KEY": "${MY_API_KEY}"  // 从环境变量读取
      }
    }
  }
}

MCP server 限制可访问目录：

{
  "mcpServers": {
    "filesystem": {
      "command": "npx",
      "args": [
        "-y",
        "@modelcontextprotocol/server-filesystem",
        "/Users/you/articles",  // 只允许访问这个目录
        "--readonly"            // 只读模式
      ]
    }
  }
}

审阅结果人工复核：

自动化审阅可能误判。建议：
- 禁用词检查报告只作为参考，人工确认后再改
- 技术审阅的结果，让作者自己决定是否采纳

5.5 渐进式自动化建议

不要一次性把所有环节都自动化。建议顺序：

  1. 先自动化最频繁、最机械的步骤
    - 格式化（每次都要做）
    - 封面生成（每次都要做）
    - 这些步骤出错概率低，自动化收益高

  2. 再自动化需要人工复核的步骤
    - 禁用词检查（误报可以忽略）
    - 技术审阅（结果需要人工判断）

  3. 最后自动化跨阶段编排
    - 完整流水线
    - 条件分支

何时停止自动化：

  • 边际收益递减：花在调试自动化上的时间，比手动操作还多
  • 灵活性下降：每次调整都要改配置，不如手动快
  • 维护成本过高：配置文件比实际工作还复杂

记住：自动化的目的是省心，不是炫技。如果一个流程每月只跑一次，手动做可能更划算。

总结

Claude Code 的自动化工作流，核心是理解三驾马车的边界：

  • Hooks：轻量级事件触发，适合「在某个时机自动执行脚本」
  • MCP：外部能力扩展，适合「让 Claude 访问数据或工具」
  • Skills：任务封装复用，适合「复杂多步骤流程」

组合使用，就能搭建出真正省心的自动化流水线。

这篇文章以内容生产为例，但思路可以迁移到任何场景：代码审查流水线、项目脚手架、数据报表生成……关键是拆解阶段、明确边界、渐进式自动化。

完整的配置文件和脚本，都可以在这个仓库里找到。 照着抄作业，再根据自己的需求调整，就能跑起来。
