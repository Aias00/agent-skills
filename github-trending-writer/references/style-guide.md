# GitHub Trending 中文稿风格说明

## 目标风格

这类稿子的目标不是“机械翻译 README”，而是：

- 先让读者知道“这个项目为什么会冲上 Trending”
- 再把项目真正做什么讲清楚
- 最后补适量背景和判断

默认风格应更像：

- 热门开源项目整理稿
- 面向中文读者的二次编辑稿
- “仓库原始信息 + 适量解读”

不是：

- 纯仓库广告
- 过度夸大的行业报道
- 脱离 README 内容的自由发挥

## 推荐结构

### 1. 标题

推荐样式：

- `GitHub 热榜：...`
- `GitHub Trending：...`

标题要把项目定位说清楚，不要只写成空泛判断。

### 2. 顶部信息卡

推荐保留：

- `[!AI] [!推荐]`
- `::: info`

信息卡里建议写：

- 来源：GitHub Trending
- 仓库名
- 语言
- Star 增量
- 仓库链接

### 3. 开头

开头先回答这两个问题：

1. 这个项目在做什么
2. 为什么今天值得看

推荐句式：

- “今天在 GitHub Trending 上看到一个很典型的项目……”
- “这不是一个单纯的 demo，它真正有意思的是……”
- “它上榜不只是因为 star 增长快，而是因为它踩中了……”

### 4. 正文展开

默认按 3 种方式选一种：

- 工具型仓库：`定位 -> 能力 -> 用法 -> 为什么会上榜`
- 框架/平台型仓库：`解决什么问题 -> 架构或核心机制 -> 适合谁`
- 资源集合型仓库：`内容组成 -> 价值 -> 局限`

## 解读型稿子

适合：

- 热点开源工具
- AI 基础设施项目
- 开发效率工具

要求：

- 先用中文讲清楚仓库核心定位
- 不要大段直译 README
- 允许补少量背景，但不要掩盖仓库本身

## 翻译整理型稿子

适合：

- README 写得很完整的项目
- 上手步骤、能力边界很清楚的仓库
- 用户明确想先看原文内容

要求：

- 尽量保留 README 逻辑
- 合并重复描述
- 用中文重组，而不是逐段生硬翻译

## 不该做的事

- 不要把一个模板仓库写成完整产品分析
- 不要把 star 增长直接等同于“项目成熟”
- 不要把 README 里的未来规划写成已经实现
- 不要删掉仓库的限制条件和适用边界
